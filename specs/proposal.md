## 1. 项目目标

基于已运行过的 LeapShop/LeapChess 单镜像全栈架构，为海外 B 端客户建设一个低流量、低并发的标准产品（棋盘等）展示与采购站点。业务以现货标准产品为主线；礼品定制不再是整站定位，而是收敛为商品标签之一（与“降价促销”等标签并列），前台展示、后台配置，用于区分定制品与普通产品。新计划必须优先复用已验证的简单架构，同时修复旧基线的安全与稳定性缺陷，并明确处理旧系统不具备的多语言和 B2B 询单能力。

本阶段目标：

1. 以源码而非历史知识库为准，建立可信的旧生产能力清单；
2. 区分可直接继承、必须修复、可选改造和新业务缺口；
3. 为后续技术选型与开发任务提供有优先级的决策入口；
4. 保持约 20 并发测试站所需的最小复杂度。

本阶段不直接修改 `../LeapShop` 源码，也不宣称新 B2B 站已经具备旧站能力。

## 2. 业务背景与规模

| 维度 | 已知情况 | 架构含义 |
|---|---|---|
| 业务形态 | 标准产品采购为主（棋盘等），定制/促销等为商品标签 | 保留现有商品模型与分类，新增商品标签（如“降价促销”“可支持定制”）用于前台展示与后台配置 |
| 我方角色 | 供应链方 | 重点是建立信任、展示能力、承接需求 |
| 客户类型 | 海外 B 端客户 | 多语言、联系方式与询单路径重要 |
| 获客方式 | 主动触达后的定向访问 | 无自然集中流量，无需高并发架构 |
| 项目阶段 | 公司测试站点 | 应优先低成本、易部署、可维护 |
| SKU 规模 | 200+ | 需要数据库级分页、索引与图片容量控制 |
| 峰值并发 | 约 20 人 | 单进程 Node.js + 单服务部署足够 |
| 多语言 | 硬需求，语种未定 | 旧系统完全缺失，必须作范围例外或调整需求 |
| 交易语义 | B2B 询单，非在线零售 | 旧购物车导出不能等同于询价闭环 |

## 3. 已核验的旧生产能力

### 3.1 可复用能力

- 单镜像同源部署：Express 同时托管 API、前端与上传图片；
- PostgreSQL/SQLite 双驱动、本地零配置、幂等建表与种子；
- 图片 SHA1 落盘、目录分片、URL 入库、不可变缓存与无引用清理机制；
- 商品、轮播、全站设置、主推款、账户、审计与存储监控；
- admin/tester/demo 三角色与公开读、鉴权写的权限模型；
- 8 页原生 ESM 前台、隐藏后台、购物清单导出；
- Docker + Zeabur + PostgreSQL + Volume 部署方案。

### 3.2 旧系统实际边界

- 数据模型是 5 张表：`users/products/slides/settings/activity_logs`，不是旧 specs 所写的 4 张；
- 主推款是 `hero_products` 数组（最多 4 个），不是单一 `hero_product_id`；
- 商品接口已支持可选 `limit/page`，但数据库仍全量读取后在内存分页；
- tester 可编辑商品、轮播和设置，demo 只读；注册接口仅 admin 可用；
- 旧系统无多语言、无后端订单或询价单、无细粒度 RBAC；
- PowerShell 冒烟脚本仍依赖已删除的 customer/C001，不能视为有效回归基线。

## 4. 需求范围与优先级

### 4.1 P0：开工前必须处理

| 需求 | 验收意图 | 类型 |
|---|---|---|
| 确认 i18n 是否作为 C1 例外 | 新站必须能满足已声明的多语言硬需求，或明确撤销该需求 | 产品决策 |
| 确认 B2B 询单范围 | 明确是本地“需求清单”还是可提交、可管理的后端询价单 | 产品决策 |
| 确认品牌、分类和页面范围 | 保留 LeapShop 现有标准产品分类，新增商品标签机制（促销/定制等） | 产品决策 |
| 修复危险文件删除路径 | 任何编辑者输入都不能导致删除上传目录外文件 | 安全 |
| 建立统一异步错误边界 | 后端异常必须返回统一 500，不得使请求挂起或进程因未处理 rejection 退出 | 稳定性 |
| 消除固定生产密钥/公开默认密码 | 生产缺少密钥时拒绝启动；登录页不展示凭据；预置主账号 `P001/123456` 仅作首次启动引导，首登强制改密并初始化 | 安全 |
| 修复变体更新拼写错误 | 携带 `variants` 的商品更新能够成功并受测试保护 | 缺陷修复 |
| 重构后台访问入口 | 移除空格隐藏手势；仅通过直接 URL `/admin.html` 进入，前台不提供导航链接或公开跳转 | 产品决策/安全 |
| 确立主账号/子账号权限模型 | 主账号 `P001` 拥有全部权限并独占子账号管理；子账号按权限矩阵授权、默认仅商品 CRUD、不能访问账号管理 | 产品决策 |
| 扩展操作审计 | 自动记录登录/退出时间戳、商品增改删的时间与操作人用户名；主账号可查全部子账号及自身记录并按时间/用户筛选；持久化入库。IP 首版可选 | 产品决策/安全 |

### 4.2 P1：首个可发布版本

| 需求 | 验收意图 | 类型 |
|---|---|---|
| 恢复可信自动化测试 | 覆盖三角色权限、核心 CRUD、错误路径与安全回归，并由 CI 自动运行 | 质量 |
| 数据库级分页 | 200+ SKU 分页不再读取和解析全表 | 性能 |
| 集中输入校验 | 分类、数值、图片 URL、设置值等有统一边界 | 安全/数据质量 |
| CORS 与限流 | 仅放行受信域名；登录和写接口具备合理限频 | 安全 |
| LOGO 引用纳入清理 | 共用哈希图片时不会误删 LOGO | 缺陷修复 |
| 图片上传协议决策 | 明确继续 base64 或迁移 multipart，并给出客户端兼容策略 | 技术决策 |
| 契约基线更新 | API、角色、表和分页语义与源码一致 | 规格质量 |
| 双价与起订量入库 | `original_price`/`current_price`/`moq` 经版本化迁移落库并写入 openapi.yaml（ADR-0006） | 规格质量 |
| 前台文案英文化 | 硬编码 UI 文案统一英文，内容字段保留业务语言 | 产品决策 |

### 4.3 P2：质量与长期演进

异步 bcrypt、结构化日志与请求 ID、Token 撤销、版本化数据库迁移、TypeScript/ORM、前端构建策略、E2E 测试均在 P0/P1 完成后按决策推进。

## 4.5 Phase 2 实施范围（当前轮次）

Phase 1（v0.1–v0.3）完成规格梳理、基线核验与产品决策；Phase 2 进入本仓库的实际实施。本轮范围如下（每项对应 design §8 与 tasks I1～I5）：

| 范围 | 内容 | 类型 | 关联 |
|---|---|---|---|
| P0 后端安全修复 | 异步错误边界（`wrapAsync` + 终端错误中间件）、`removeUnreferenced` 路径遍历防护、`materializeVariants` 拼写修复、生产环境 `JWT_SECRET` 强制检查 | 安全/稳定性 | K1～K4、design §8.3–§8.5 |
| 持久化存储配置 | Dockerfile 设置 `DATA_DIR=/data`、`UPLOAD_DIR=/data/uploads` 对齐 Zeabur Volume 挂载点；启动时验证卷可写；管理后台展示卷容量 | 部署/运维 | design §8.2 |
| 遗留代码清理 | 种子资产从 `frontend/sandbox/prototype-f/assets/` 迁移至 `backend/seed-assets/`；删除整个 `frontend/sandbox/`、`tools/dev-server.mjs` 与过时文档 | 仓库卫生 | design §8.1 |
| 管理后台视觉打磨与关键 UX | 设计令牌（间距/字号/表面）、IntersectionObserver 激活导航、样式化对话框替代原生 confirm/prompt、面板骨架屏、排版一致性 | 前端体验 | design §8.6 |
| 后端逻辑增强 | 数据库级分页、批量存储统计接口 `/api/stats/products-storage`、批量设置更新 `PUT /api/settings/batch` | 性能/接口 | K7、design §8.7–§8.8 |

**本轮明确不做**（延期至后续阶段）：多语言 i18n、B2B 询单后端、TypeScript/ORM、multipart 上传、E2E 测试与 CI。

## 5. 核心约束

- **C1 · 控制新增模块**：默认只继承或改造旧模块；多语言、B2B 询价，以及本轮确认的主账号/子账号权限矩阵与审计增强，因是已声明业务需求，均须通过明确决策（见 ADR-0004、ADR-0005）成为例外后才能设计和实现。
- **C2 · 改进须论证**：改造项需说明原因、技术方案、适用范围、收益与代价。
- **C3 · 视觉后置**：品牌和页面范围确认前，不锁定视觉样式与具体布局。
- **C4 · 拒绝过度设计**：约 20 并发阶段不引入 Redis、消息队列、微服务、负载均衡或分布式追踪。
- **C5 · 源码为事实源**：生产能力以指定提交的源码和可重复测试为准；架构文档与 repowiki 仅作说明和历史参考。
- **C6 · 安全缺陷不继承**：复用旧架构不等于复制其已知 P0/P1 缺陷。
