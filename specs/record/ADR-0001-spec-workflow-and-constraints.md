# ADR-0001 · 规格工作流与核心约束

- **状态**：已采纳（Accepted）
- **日期**：2026-09-05
- **相关文档**：[proposal.md](../proposal.md)、[design.md](../design.md)

## 背景（Context）

本仓库是从上一个项目迁移而来的知识库（`repowiki/`）。用户希望基于对旧架构的梳理，为一个**新站点（B2B 定制礼品采购）**协作产出规格文档 `/specs`，且强调：**先规划、再编码**，本阶段**不写任何源代码**。

## 决策（Decision）

### D1 · 文档结构
采用用户指定的结构：

```
specs/
├── proposal.md   # 需求文档
├── design.md     # 架构设计（本轮=现状梳理+改进探索）
├── tasks.md      # 任务清单
├── contracts/    # 接口契约（yaml + md）
└── record/       # 决策修改记录（ADR）
```

### D2 · 本轮核心约束（必须遵守）
- **C1 不新增模块**：不允许增加任何原项目不存在的功能或模块；改进方向只能基于现有模块做技术/质量/安全/性能层面的改造。
- **C2 四要素论证**：任何改进方向一经提出，必须附「原因 / 技术点讲解 / 适用范围 / 改后好坏」。
- **C3 不碰界面细节**：本轮不涉及交互、样式、界面布局。
- **C4 拒绝过度设计**：一切建议须匹配「约 20 并发、低流量测试站」的真实规模。

### D3 · 半成品定位
本轮产出为 **v0.1 半成品**：目标是「看清原架构做了什么 + 探索可改进方向」，**不锁定完整新方案**。design.md 以「保留/观望/缺口/过度设计」四态分类，改进项以待决策清单形式交回用户拍板。

## 影响（Consequences）

- ✅ 正面：约束明确，避免过早引入新复杂度；改进建议有据可查；决策权保留在用户手中。
- ⚠️ 代价：**多语言（i18n）** 作为新站点硬需求，因 C1 无法在本轮设计，只能登记为缺口（见 proposal Q1 / design §5）——此为**约束与需求的已知张力**，需用户确认处理方式后才能推进完整方案。
- 后续：待 design §6 决策清单与 proposal §5 待确认项拍板，产出 v0.2 并填充 contracts/ 与 tasks.md。

## 后续更正（2026-10-12）

本 ADR 背景中“新站点（B2B 定制礼品采购）”的定位已被 [ADR-0004](./ADR-0004-scope-standard-products-and-tags.md) 取代：新站以标准产品（棋盘等）采购为主线，定制与促销等统一收敛为商品 `tags` 标签（前台展示、后台配置）。C1～C4 约束本身继续有效。
